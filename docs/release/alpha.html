Rust 版 dimcode 发布 alpha

正式版和 beta 是 npm 包 dimcode（命令 dim），alpha 是单独的包 dimcode-alpha（命令 dima）。两个包可以同时装，互不覆盖；每个通道只在自己内部升级。

让 agent 代办时，CI 发版和版本 PR 使用 dim-release；dim-alpha-release负责选择 alpha 路径，只有明确选择本机 Mac 时才执行本机发布命令。用法与版本字段见发布文档。

让 agent 准备版本或发版

可以直接使用下面的请求。若 agent 没有列出对应 skill，让它读取上面链接指向的仓库 SKILL.md 即可。

使用 $dim-release，准备下一个 alpha 的版本 PR。
查询所有相关 npm 包和远端 tag，选择未使用的版本，同步版本字段并验证。
只开 PR，不合并、不打 tag、不触发构建、不发布。

使用 $dim-release，为 main 上已通过 CI 的发版提交构建 GitHub prerelease 草稿。
检查产物后停在草稿，不公开 Release，不发布 npm。

使用 $dim-release，把现有 GitHub prerelease vX.Y.Z-alpha.N 发布到 npm。
沿用原始产物，通过配置好的 OIDC 工作流发布，不重新构建。

使用 $dim-alpha-release，仅在本机 Mac 做 dry run，允许编译和校验。
不发布 npm，不创建 GitHub tag 或 Release。

手动准备版本 PR 时，先把统一版本号提交到 Cargo.toml、Cargo.lock、npm 外壳和 runtime 元数据，再合入 main、打对应的 vX.Y.Z-alpha.N tag。完整字段见版本准备。本机脚本则临时改版本、结束时还原，两条路径不能混用。

通道规则

版本号npm dist-tag安装 / 升级当前用途
X.Y.Zlatestnpm i -g dimcodeTS 版正式
X.Y.Z-beta.Nbetanpm i -g dimcode@betaTS 版 beta
X.Y.Z-alpha.Nalphanpm i -g dimcode-alpha@alpha，命令 dimaRust 版

scripts/publish-npm.mjs 按版本号自动选 dist-tag 和外壳包：alpha 发 dimcode-alpha，只带 dima 命令；其他预发布标识（例如 rc）直接拒绝。平台包 dimcode-<平台> 和 dimcode-web 两边共用，外壳包锁定精确版本。alpha 构建默认使用独立的数据目录 ~/.dimcode-alpha，不读写 dim 的 ~/.dimcode。

alpha 版本号必须低于 npm 上最新的 beta。 已装的 TS 版 beta 会自动升级到所有预发布版本里最高的那个，不区分 alpha 和 beta。所以只要 alpha 版本号高过最新 beta，beta 用户就会被拉到 Rust 版。 publish-alpha.mjs（编译前）和 publish-npm.mjs（写入 npm 前）都会检查这一点，不满足就停下。 Rust 版从 0.1.0-alpha.0 起步，远低于 TS 版的 0.5.x，所以目前不受影响。

beta 要不要重新发布？

不用。TS 版的发布脚本一直用版本号里的预发布标识作 dist-tag，现有的 0.5.20-beta.0 已经在 beta 上。latest 和 beta 都不受 alpha 发布影响。

只有想去掉上面那条「alpha 必须低于 beta」的限制时，才需要在 TS 仓库改 packages/cli/src/core/upgrade/update-version.ts，让预发布轨道只选同一标识的版本，然后发一版 beta。这个改动只对升级到新 beta 的用户生效，没升级的老版本仍按旧逻辑选。

GitHub 托管 runner 构建和发布

手动从 main 准备下一个 GitHub alpha。若该提交已有 alpha tag，或等于 npm 上一个 alpha 的源提交，工作流就跳过。否则它自动取号，由 GitHub 托管 runner 按目标系统和架构构建六个平台，并在 Ubuntu 构建 Web，把原始压缩包、清单和校验和上传到 prerelease 草稿。

gh workflow run release.yml --ref main

检查附件并在 GitHub 发布 prerelease，然后用它的真实 tag 运行 npm 工作流。GitHub 托管 runner 通过 OIDC 发布 Release 附件。验收任务安装 dima、核对旧包标签，并确认八个包在阿里 npm 镜像上可用。见发布配置与重试说明。

gh workflow run npm-publish.yml --ref main -f release_tag=vX.Y.Z-alpha.N -f publish=true

本机替代方案：一条命令 build + 发布

和 TS 版的 bun publish:bin 一样，在本机 Mac 上一次完成编译、打包和发布：

npm login --registry https://registry.npmjs.org   # 第一次
node scripts/publish-alpha.mjs                       # 自动取下一个 alpha
node scripts/publish-alpha.mjs 0.1.0-alpha.3         # 指定版本
node scripts/publish-alpha.mjs --dry-run             # 只编译和校验，不发布
node scripts/publish-alpha.mjs --platform darwin-arm64  # 只发指定平台（可重复），主包只引用这些平台
选版本→临时改版本号→编译 6 个平台→打包校验→发布 npm @alpha→清理
  1. 选版本 没指定版本时，取 npm 上最高的 alpha 加 1。比较范围包括 dimcode-alpha、dimcode-web、6 个平台包和旧的 dimcode，所以发到一半失败的版本号不会被重复使用。一个 alpha 都没有时，用 <Cargo 版本>-alpha.0。 以下情况直接拒绝：版本已经在 npm 上、alpha 高过最新 beta、工作区有未提交改动（--dry-run 除外）、磁盘剩余不足 8 GiB。
  2. 临时改版本号 编译前一次改齐 Cargo.toml、Cargo.lock、npm/package.json（含 6 个 optionalDependencies）、runtime/package.json、runtime/package-lock.json，结束时（不论成功失败）全部还原。不提交，仓库里的版本号保持不变；包里记录的源提交就是当前 HEAD。构建时设置 DIM_RELEASE_BUILD=1，所以发布出来的二进制报的是这里设的版本；没有这个标记的构建（例如直接 cargo build）报的是仓库里提交的版本加 -source，如 0.1.0-alpha.8-source。
  3. 编译 6 个平台 macOS 两个架构用 cargo；Linux（glibc 2.28）和 Windows 用 cargo-zigbuild 交叉编译。需要先装好 cargo install --locked cargo-zigbuild 和 zig。 注意：Windows 本地用的是 *-windows-gnu / gnullvm 工具链，CI 正式版用的是 MSVC。
  4. 打包校验 复用 CI 同一套脚本 stage-plugins.mjs、stage-release.mjs、pack-release.mjs、collect-release.mjs，生成 6 个平台包、dimcode-web 和 dimcode-alpha 包，并校验版本、源提交和 sha256。默认插件只 stage 一次（--portable 会在安装前拒绝 lock 里带 os、cpu 或 libc 的插件包），每个平台包都带同一份 default-plugins.json 和 plugins/。
  5. 发布 npm publish-npm.mjs --publish-local 先发 6 个平台包和 Web，最后发 dimcode-alpha，全部打 alpha tag，然后打印 dist-tags。开了 2FA 的话每个包都会提示输入 OTP。 --publish-local 只接受 alpha；本仓库尚未配置 Rust beta 和正式版的 CI 发布。
  6. 清理 见下一节。

磁盘清理

一次 release 编译每个目标要占几个 GB，6 个目标同时留着会把磁盘占满，所以脚本同一时间只保留一个目标的缓存：

  • 每个平台打完包就删除 target/<triple>。代价是下次发版要从头编译。
  • 中间产物用完即删（stage/、platforms/、原生包）。
  • 启动时删除所有 staging/alpha-*；结束时（不论成功失败）删除本次的 staging/alpha-版本号 和各目标的 target/<triple>，staging/ 空了也一并删掉。只有 --dry-run 保留打好的包供检查。

每次运行结束（不论成功还是失败），只要本机装了 mbx，就会自动执行一次 mbx gc。target/ 由 mbx 管理时，它会按 mbx 自己的预算回收共享编译缓存和长期不用的 target，清理失败也不影响发布结果。脚本本身不会去删开发用的 target/debug、target/release。

账号插件：默认打出来的 alpha 不带 Dim 账号，只支持 API key。要带账号，运行前设置 DIM_OAUTH_CLIENT_ID_CN 和 DIM_OAUTH_CLIENT_ID_GLOBAL（不要提交到仓库）。

本机发布后验证

npm view dimcode-alpha dist-tags
npm i -g dimcode-alpha@alpha && dima --version
git status # 应该是干净的

应看到 dimcode-alpha 的 alpha 指向新版本，dimcode 的 dist-tag 没有变化，dim 仍是原来的版本。以前装过 dimcode@alpha 的用户不会再收到 alpha 升级，需要手动装一次 dimcode-alpha@alpha。

本机命令出错时

  • 任何一步失败：修好后原样重跑同一条命令。重跑会从头编译，并取下一个版本号；发到一半的那个版本号作废，不会再用。
  • alpha 版本号高过 beta 被拦：显式指定一个更低的版本。不要去改这条检查。
  • 某个平台编译失败：修好后重跑。没加 --platform 时，6 个平台包缺一个都不发。

CI 重试遵循 dim-release：源码不变时重试同一 tag 和原始 Release 包；源码变化才使用新版本。不要把本机命令“重新选下一版”的恢复方式套到 CI 发布。
