# 请求增量存储（原生格式 v17）

状态：已在 [#224](https://github.com/arcships/dim/pull/224) 实现，原生格式 v17。实现修正了四处表述，各在其所在位置：准备阶段同时序列化新节点（§6.1），请求行序列化其事件时不含请求内容（§6.1、§6.3），一个读取器服务整个校验轮（§7.1、§7.2），验收阈值以测量报告而非断言（§18）。[#193](https://github.com/arcships/dim/issues/193) 的第 2 阶段，按该 issue 最新评论中商定的方向。第 1 阶段是在一次读取的各页之间共用有界内容缓存，已以 [#213](https://github.com/arcships/dim/pull/213) 合入；第 3 阶段是另一份运行时提议（§15）。负责线：Agents/存储（yyhhyyyyyy）。评审：zerob13、eric8810。范围：原生 `TimelineStore` 实现内部（`SqliteTimelineStore`，[timeline.rs](../../../../crates/dim-app-server/src/storage/timeline.rs) 与 [codec.rs](../../../../crates/dim-app-server/src/storage/codec.rs)），以及本设计将其升级到 v17 的[存储格式](../../../design/appserver/native-storage-format.md)。本修订用内容表中的消息列表取代初稿中请求行之间的增量（§16 D1、§17）。

## 1. 概要

v16 格式中，`context/prepare` 或 `model/call` 行为请求的每条消息保存一个内容哈希引用。每个请求重复上一个请求再追加几条消息，所以第 k 次模型调用保存 k 个引用。存储、写入时的哈希和读取时的解码，都随两次压缩之间模型调用次数的平方增长（§2）。

- **规则。** v17 保留 v16 中事件行与 Session 内容行的划分，只改变请求行引用其消息的方式：由每条消息一个引用改为引用一个列表。列表节点是一条内容行，保存一条消息和它前一个节点的内容地址，所以消息前缀相同的请求共用这段前缀的节点。请求行保存最后一个节点的地址和列表长度，另外照旧保存 v16 的 `tools` 与 `system` 引用。写入请求时，只为它与同一分支上一个请求的公共前缀之后的每条消息新增一个节点（§5）。
- **确定性。** 节点按内容寻址，字节是分支逻辑历史与该事件的函数。每分支一份的写入方记忆只省去回读上一个请求（§6）。
- **读取。** 请求只由它自己的行和它自己的列表还原，从不经过其他事件行。一次读取保留上一个还原的请求，只加载该请求没有的节点；冷读取一个请求时每条消息加载一个节点（§7）。遍历列表时每加载至多 256 个节点就释放一次连接。因此从 `resume` 起的检查点读取不读取 `resume` 之前的任何请求行，只读取现在的读取所返回的行（§10）。节点缺失或损坏时读取失败；请求绝不会被还原为空（§8）。
- **测量。** 在 mock、工具与产品窗口三种配置下，压缩之外的每个请求都延续上一个请求，且写入下一个请求时上一个请求总还在内存中（§4）。约 10,000 条事件时，v16 每条事件存储 13,778 字节，v17 将为 411 字节，与 1,000 条事件时大致相同（普通 mock 轮次；§12）。
- **格式。** v17 是在现有准入事务内把标记从 v16 原地改为 17，不改表、不改写任何行；`timeline_content` 增加 `node` 种类。v16 行永久可读，v16 与 v17 行可在同一数据库中混存（§11）。

事件类型及其冻结样本、Timeline、Dispatcher、`TimelineStore` trait 及其读取语义、能力和外部协议都不变；§3 逐条写明保持每项存储约定的机制。不新增事件、服务、方法、wire 字段、配置或运行时需求。

## 2. 问题与依据

### 2.1 恢复耗时（#193）

release 构建，Apple M4，一次性数据库上的 `SqliteTimelineStore`，`defaults::mock_hosts` 与 `defaults::install`。历史经 mock 模型轮次增长（普通轮写 10 条事件，工具轮写 18 条）；每个规模恢复 7 次。计时：`Agent::restore_session` 加第一次 `idle("main")`。

| 事件数 | 普通轮，中位数 | 工具轮，中位数 |
| --- | --- | --- |
| ~1,000 | 65 ms | 80 ms |
| ~3,000 | 327 ms | 404 ms |
| ~10,000 | 2.77 s | 3.48 s |

10,017 条普通事件时，2,772 ms 中有 2,186 ms 花在 11 次全历史读取（每次约 199 ms），549 ms 花在 `validate_session`。每个请求行为每条消息保存一个引用（`encode_refs`），所以 10k 条事件时这些行共有 2,000,000 个引用、137.5 MB 事件行，而不同内容只有 2,001 条；解码要经 `ContentCache` 解析每个引用。

### 2.2 第 1 阶段（#213）

第 1 阶段用一次 `foldhash` 查找解析一个引用，并让一次读取的各页、一轮 `validate_session` 共用一个缓存，缓存正文上限 64 MiB。写入方与写出的字节不变。其结果（两轮交错测量的平均值，每轮取 7 次恢复的中位数）：

| 组合 | 事件数 | 恢复加首次 idle | 每次读取 | `validate_session` |
| --- | --- | --- | --- | --- |
| 普通 | ~1,140 | 71 → 58 ms | 5.0 → 4.3 ms | 9.7 → 5.3 ms |
| 普通 | ~3,140 | 344 → 245 ms | 25.2 → 19.6 ms | 58.6 → 22.1 ms |
| 普通 | ~10,140 | 2,866 → 1,779 ms | 208 → 146 ms | 576 → 149 ms |
| 工具 | ~1,140 | 80 → 71 ms | 5.7 → 5.3 ms | 11.5 → 6.5 ms |
| 工具 | ~3,130 | 417 → 303 ms | 30.5 → 24.3 ms | 73.3 → 27.8 ms |
| 工具 | ~10,140 | 3,624 → 2,256 ms | 257 → 184 ms | 724 → 186 ms |

### 2.3 剩下的问题

把第 1 阶段普通轮的每次读取耗时拟合为 `a·E + b·R`（`E` 为事件数，`R` 为引用数，`T` 个普通轮时为 `2T² + 4T`），得到每条事件 a ≈ 2.9 µs、每个引用 b ≈ 58 ns；该拟合复现了 1,140 条事件的读取（4.5 ms，实测 4.3 ms）。10k 条事件时，每次读取的 146 ms 中有 117 ms 花在引用上。只有改格式才能去掉它们。

写入同样付出代价。每个请求行，v16 写入方序列化每条消息、tools 与 system prompt 并计算 SHA-256，再为每份内容执行一次 `INSERT OR IGNORE`。在 10k 条事件的普通 Session 的最后 200 个请求行上，SQL 之前每行要 542 µs，v17 编码（含前缀比较）为 13 µs（§6.3）。每个模型步骤还读取两次上下文历史（[timeline-storage §4](../../../architecture/rust-agent/timeline-storage.md#4-读取)），没有压缩时，这两次读取要解码此前所有请求。

存储建成时的检查使用频繁压缩，请求列表一直很短。两次压缩之间有大量模型调用的情况不在那次检查的范围内：mock 与 `--models` 配置从不压缩，而窗口较大时，基于 token 的压缩可能相隔数百步。

## 4. 前缀稳定性

### 4.1 为什么相邻请求互相延续

只有每个请求以前一个请求开头，共享才有收益。三项现有合同保证两次压缩之间如此：

- **投影只追加。** 事件只经已采用的输入与工具结果进入模型上下文（AGENTS.md 规则 10，[设计规则 §4](../../../architecture/rust-agent/principles.md#4-通过时间线扩展行为) 第 6 条），历史渲染把它们放在末尾。`context/prepare` 的请求就是其 `through` 处渲染出的历史。
- **准备只能追加。** ContextPreparation 拒绝不以渲染历史开头的准备结果（“Context preparation must preserve the timeline history prefix; additional messages may be appended”，[context_preparation.rs](../../../../crates/dim-agent-capabilities/src/context_preparation.rs)）。因此除非 ContextPolicy 在中间压缩，`model/call` 的请求延续其 `context/prepare`。
- **ContextPolicy 已依赖这一点。** 它的 provider 基线只在 `request.messages` 以上一个 `model/call` 的消息开头时适用。

完成的压缩替换列表开头（replacement、基线、保留的尾部），所以压缩后的那个请求与上一个请求没有公共前缀，开始一个新列表（§10）。`system` 或 `tools` 变化（prompt 修订、工具采用）时，为新值写一条内容行。

### 4.2 测量

一个临时探针（不提交）在一次性数据库上用转发的 `TimelineStore` 包住 `SqliteTimelineStore`。每次 `append` 时，它把每个请求与同一分支上的上一个请求比较：先 `Arc::ptr_eq` 再 `==` 求公共前缀，比较 `system` 与 `tools`，并检查上一个请求的 `Arc` 是否仍然存活，也就是 `Weak` 记忆会看到的情况。它还构建精确的 v17 节点与引用。release 构建，Apple M4。配置：

- **普通**与**工具**：`defaults::mock_hosts` 与 `defaults::install`，使用 [`restore_cost`](../../../../crates/dim-app-server/examples/restore_cost.rs) 的轮次；不压缩。
- **产品窗口**：产品窗口事实（`ProductContextModel`）与摘要策略（`ProductSummaryStrategyPlugin`）、`IdentityContext`、`HistoryRenderer::default()`、`MockTools`，以及窗口 32,000 token、输出 2,000 token 的能力快照。模型驱动像 `EchoModel` 一样回显，对摘要请求回答一段每次不同的简短摘要。轮次在普通文本与 `tool:echo` 之间交替，每轮带 1,000 字节，所以窗口会填满，约每 20 轮压缩一次。

统计每一个请求行：

| 配置 | 事件数 | 请求行 | 新列表（完成的压缩） | 保留上一个请求全长的行 | 保留消息 / 消息总数 | 每行新节点数 | 追加时上一个请求仍存活 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 普通 | 1,001 / 3,001 / 10,001 | 200 / 600 / 2,000 | 1（0） | 100% | 99.0% / 99.7% / 99.9% | 1.00 | 100% |
| 工具 | 1,009 / 3,007 / 10,009 | 224 / 668 / 2,224 | 1（0） | 100% | 99.1% / 99.7% / 99.9% | 1.00 | 100% |
| 产品窗口 | 3,007 / 10,017 | 578 / 1,926 | 10（9）/ 33（32） | 98.4% / 98.3% | 97.4% / 97.4% | 1.45 / 1.48 | 100% |

“保留上一个请求全长的行”统计除第一个请求外的每个请求行；产品窗口中其余的恰好是完成压缩后紧接的 9 行和 32 行。按行看，`model/call` 不新增节点，`context/prepare` 新增两个（模型输出与下一条输入或工具结果），第一个请求新增一个，该配置中压缩后的请求新增十个。

- 除压缩之后紧接的请求外，每个请求都延续上一个请求：`keep` 等于其长度。每个新列表要么是 Session 的第一个请求，要么紧跟一次完成的压缩。
- `model/call` 保留其 `context/prepare` 的消息 `Arc`，所以它的前缀按指针找到。`context/prepare` 与上一个 `model/call` 没有共享指针：渲染每一步都构建新消息，所以它的前缀按 `==` 找到。值比较计入 §6.3 的 v17 写入成本。
- 普通与工具配置中，`system` 与 `tools` 在第一个请求之后从未变化。
- 每次追加请求时（包括 Session 空闲后新一轮的第一个请求），同一分支上的上一个请求都仍然存活。探针观察的是存活与否，不是由谁持有；ContextPreparation 与 ContextPolicy 各自保留最近一个已准备的请求，Timeline 也在热窗口中保留近期事件。因此运行中的 Session 里，`Weak` 记忆总能命中。
- 没有一次运行在 before 轨迹中出现请求。

### 4.3 未测量的部分

- 真实 provider 适配器（`ModelProviderPlugin::process`、aimux）与非恒等的准备宿主：这些配置使用 `IdentityContext` 和回显驱动。准备规则允许宿主为每个请求追加消息，这样的宿主会在每个 `model/call` 行里为这些消息新增节点。
- Session 期间的 prompt 来源修订与工具采用：按构造，每次各写一条 `system` 或 `tools` 内容行。
- 请求事件上的 before 回调：产品装配没有注册（只有测试在 `model/call` 上注册）。草稿由验收测试覆盖（§18）。
- TypeScript 插件，以及用真实模型的 CLI 产品配置。

**假设。** 同一分支上的相邻请求在两次压缩之间互相延续。如果某个生产方每一步都改写一条早期消息，每个请求就要从第一条变化的消息起为每条消息新增节点，每行的存储又会随请求增长：按消息字节增长，而 v16 是按每个引用 67 字节增长。冷读取一个请求仍只加载它自己的节点（§7.4）。目前产品中没有这样做的地方。那样做也会使 provider 的提示词缓存与 ContextPolicy 的基线失效，ContextPreparation 也已拒绝准备宿主这样做。§18 的验收测量每条事件的字节数，出现退化时能看出来。

## 5. 编码

### 5.1 列表与上一个请求

- **请求事件**：`context/prepare` 或 `model/call` 事件；其 `data.request` 就是请求。before 轨迹中的草稿从不作为其他记录的上一个请求。
- **节点**：种类为 `node` 的 `timeline_content` 行，正文为 `{parent, message}`。`message` 是 v16 `message` 正文形式（`{role, content}`）的一条消息；`parent` 是它前一条消息的节点地址，第一条消息为 `null`。其地址按 v16 的 `SHA-256(kind NUL body)` 计算。因此一个节点标识一整段消息前缀，前缀相同的请求引用相同的节点。
- 请求的**列表**：它的消息对应的节点，以最后一个节点的地址和长度引用。没有消息的请求不引用任何节点。
- 分支 `b` 的**逻辑历史**：截至各自截点的祖先前缀，然后是 `b` 自己的事件。这就是运行时根据分支目录构建的祖先链 `[(branch_id, cut)]`，存储在 `timeline_branches.info` 中以 `parent` 与 `branch_point` 保存。
- `b` 上序号 `s` 的请求事件的**上一个请求**：`b` 的逻辑历史中它之前的最后一个请求事件，即 `b` 上 `s` 之前的最后一个；没有时，取最近一个有请求的祖先上截点及之前的最后一个。
- **keep**：两个 `messages` 列表最长公共前缀的长度。每一对先用 `Arc::ptr_eq` 比较，再用 `Message` 的 `==` 比较。
- **写列表**：前 `keep` 条消息沿用上一个请求的节点；之后每条消息新建一个节点，其父节点是前一条消息的节点。`keep` 为 0 的请求（第一个请求、压缩后的请求）开始一个新列表。节点用 `INSERT OR IGNORE` 写入，与 v16 写内容相同。
- **`tools` 与 `system`**：缺省 → `null`；等于上一个请求的值（先指针再 `==`）→ 沿用上一个请求的地址，不再序列化；否则序列化、计算哈希，作为种类 `tools` 或 `system` 的 v16 内容行写入。
- **草稿**：记录 before 轨迹中的请求（`WireTrace.original`、每个非空的 `WireStep.result`）以同样方式编码，以所在记录的事件请求为其上一个请求。该请求一定存在，因为草稿与其事件同一种类。

写入方总是取紧邻的上一个请求和最长前缀，节点又是内容地址，所以字节是逻辑历史与该事件的函数。相等用类型自己的 `==`，这也是存储验收比较事件的方式（§18）。由此带来一点：消息内某个 JSON 对象值相等但序列化的键序不同时，算作保留，沿用较早的节点，读回时采用该节点的键序。相邻请求的消息由相同事件渲染，实际中不会出现，也没有读取方依赖键序。

列表没有上限，也不需要：列表恰好是它的请求的消息，所以还原一个请求只读它自己的行和它自己的节点（§7.4）。

### 5.2 持久化 JSON 类型

v16 的 `Row`、`WireTrace`、`WireStep` 与 `References` 不变。v17 为请求记录增加一种引用形式和一种内容种类：

```text
WireEvent      = { event: AgentEvent, refs: References | ListReferences | null,
                   trace: WireTrace | null, batch_end: integer }
WireDraft      = { event: EventDraft, refs: References | ListReferences | null }
References     = { messages: string[], tools: string | null, system: string | null }      v16
ListReferences = { list: string | null, length: integer,
                   tools: string | null, system: string | null }                          v17
node body      = { parent: string | null, message: Message }                    content kind "node"
```

- v17 写入方在每个 `context/prepare` 与 `model/call` 记录及其请求草稿上写 `ListReferences`。v16 请求记录保留 `References`。两种形式按字段区分，且各自拒绝未知字段。其他记录照旧为 `refs: null`，字节与 v16 写出的完全相同。
- 与 v16 相同，存储的 `data.request` 为 `messages: []` 且不含 `tools` 与 `system`；其余字段保持原位。
- `list` 是最后一个节点的地址，当且仅当 `length` 为 0 时为 `null`。
- `tools` 与 `system` 是 v16 内容地址，与 `References` 中相同。
- 地址不含 Session ID，所以分叉逐字节复制后仍然有效（§9）。

## 6. 写入

### 6.1 找到上一个请求

写入线程先收集一轮批次，再在一个事务内提交（`commit_round`）。v17 把请求记录的编码分为两步：事务开始之前，写入方按顺序准备该轮的每条请求记录；事务之内，只写入准备阶段决定的内容。对 `(b, s)` 处的请求记录：

1. **本轮更早的记录，或记忆命中。** 本轮在 `b` 上更早的记录中有请求时，其中最后一个就是上一个请求，在内存中。否则，记忆（§6.2）中有 `b` 的条目且其请求仍然存活时，该条目就是 `b` 最后一个请求行：它的请求、列表地址与长度，以及 `tools` 与 `system` 的地址。
2. **否则**写入方经存储普通的读取路径读取它：`b` 上 `s` 之前的最后一个请求行（沿主键向回扫描，只读 `kind` 列，不读正文），没有时依次在各祖先上找截点及之前的最后一个，祖先与截点取自 `timeline_branches.info`，本轮更早创建的分支则取自其分支创建记录。然后遍历该行的列表（§7.2）把它还原。上一个行是 v16 行时没有可共享的节点，写入方不还原它：新请求为每条消息写一个节点，`tools` 与 `system` 按 v16 的方式写，每个分支一次（§11）。
3. **找不到请求**：`keep` 为 0。

然后写入方在内存中计算 `keep`。第一个新节点的父节点是上一个请求位置 `keep − 1` 的节点：`keep` 等于其长度时就是它的最后一个节点（压缩之外的所有实测行都是如此），否则从最后一个节点沿父节点回退 `length − keep` 步得到。每个请求草稿按同样步骤相对所在记录的事件请求准备。

准备阶段的每次节点加载都走读取路径，每次持锁至多加载 256 个节点（§7.2）。写入线程是唯一改动已有 Session 行的线程（追加、创建回滚与删除都在它上面运行；分叉写的是新 Session），所以它读到的已提交行在其事务开始时仍是最新的。准备阶段同时把每条新消息序列化为节点并计算哈希，变化了的 `tools` 或 `system`（§5.1）也一样。事务之内，写入方用 `INSERT OR IGNORE` 写入节点，再写入变化了的 `tools` 或 `system`，最后写行；行由事件的一个副本序列化，副本中的请求不含内容。事务不加载也不序列化任何节点或请求内容，每个请求行的工作量只随新消息增长。

### 6.2 写入方记忆

每个 `(Session, 分支)` 一条：写入方在该分支上编码的最后一个请求行的序号、指向其请求的 `Weak<ModelRequest>`、其列表地址与长度，以及 `tools` 与 `system` 的地址。条目大小固定。

- 记忆不持有请求：运行时丢弃请求后，条目即失效。每轮写入结束时清除失效条目，所以记忆中每个分支至多一条小条目，且仅当其最后一个请求仍在内存中。
- 事务失败或回滚时移除所涉 Session 的条目，`rollback_session` 与删除也一样。条目被移除只让下一次写入多做一次 §6.1 第 2 步的查找。
- 记忆不决定任何字节。命中时上一个请求就是内存中那个；未命中时从存储还原它。两种情况都按值比较，保留的消息沿用上一个请求的节点，新节点是所写内容的内容地址，所以两者写出相同的字节（§18 确定性）。它是存储内部的加速，不是业务状态。

实测（§4.2）：每种配置中每次追加请求时上一个请求都存活，所以运行中的 Session 写入时无需回读。重启、卸载或分叉之后，每个分支的第一次请求写入在其事务之前还原上一个请求，每个分支一次；其成本见 §7.4。

### 6.3 每个请求行的工作量

| | v16 | v17 |
| --- | --- | --- |
| 序列化 | 整个事件（含请求），再加每条消息、tools 与 system | 不含请求内容的事件、新消息（作为节点），以及变化了的 `system` 或 `tools` |
| 哈希 | 每份序列化内容的 SHA-256 | 每个新节点及变化了的 `system` 或 `tools` 的 SHA-256 |
| SQL | 每份内容一次 `INSERT OR IGNORE`，然后写行 | 每个新节点与变化的值一次 `INSERT OR IGNORE`，然后写行 |
| 比较 | 无 | 与上一个请求求前缀：`model/call` 行按指针，`context/prepare` 行按 `==`（§4.2） |
| 实测 SQL 之前的耗时（仅内容与比较），约 10k 条事件时最后 200 个请求行的中位数 | 普通 542 µs，工具 979 µs，产品窗口 462 µs | 普通 13 µs，工具 24 µs，产品窗口 23 µs |

实测配置中 `context/prepare` 行新增两个节点，`model/call` 行不新增（§4.2）。v17 的耗时主要是对 `context/prepare` 行前缀的值比较：10k 条普通事件时这些行要 15 µs，按指针比较的 `model/call` 行为 1.7 µs。输出行合并及其他所有记录不变。

实测耗时不含行本身。v16 先把整个请求序列化为 JSON 值，再把其内容换成引用，这份复制随请求增长。v17 从事件的一个副本序列化行，副本中的请求不含内容（§6.1）。

## 7. 读取

### 7.1 按序读取

每次读取保留上一个还原的请求，以及它每条消息的节点地址：`read_segments` 或 `read_page` 每次调用一份，`validate_session` 每轮一份，像 #213 携带其缓存一样跨越该调用的各段与各页、该轮的各个分支。跨分支保留同样安全：节点地址确定了以它结尾的整个消息前缀，同一位置地址相同就是共有前缀，无论所保留的请求来自哪个分支。对 v17 请求行，读取从最后一个节点向第一个节点遍历列表。加载节点之前，先把该节点地址与所保留请求同一位置的地址比较；第一次相同时，列表的其余部分就是所保留请求的，遍历停止。还原出的请求是所保留请求到该位置为止的消息，加上本次加载的消息；其 `tools` 与 `system` 按地址经缓存加载。之后原地截断并扩展所保留的请求，事件按事件类型的要求得到自己的消息向量（§7.4）。

- v16 请求行照旧经 `refs` 与 #213 的有界内容缓存解码。此时所保留的请求没有节点地址，所以下一个 v17 行遍历其整个列表。
- 草稿以同样方式相对所在记录的请求还原，不替换所保留的请求。

因此按逻辑历史顺序的读取（`context`、`history`、完整 `local` 与恢复读取）每个节点只加载一次，只有一次调用中的第一个请求遍历整个列表。

### 7.2 单个请求

没有可匹配的保留请求时，请求遍历其整个列表：每条消息加载一个节点，每条消息从后往前各实体化一次，不触及其他请求。每个节点在加载时校验（§8）。遍历每加载至多 256 个节点就释放连接；读取调用保留已取得的消息和下一个地址，在下一次持锁时继续，就像 #213 在页与页之间保留其缓存一样，所以并发写入方至多等待一次持锁。`tools` 与 `system` 各加载一次。

这在每次读取调用中只发生一次，用于其第一个请求：从历史中间开始的页、按事件 ID 读取、`trace`、快照锚点、从 `resume` 起的检查点后缀读取、分支自己的段（与祖先分开读取）。校验轮按 ID 顺序检查各分支，所以一个分支的第一个请求遍历到遇见前一个分支保留下来的请求为止。按序检查之后，校验轮再次读取每个 completed 压缩的准备边界行；这些节点仍在 #213 的缓存中，除非缓存在此期间被清空。写入方记忆未命中时也是同样的遍历，在其写事务之前进行（§6.1）。`read_page` 用单独的读取检查调用方给出的两个边界，与 v16 相同（[timeline.rs](../../../../crates/dim-app-server/src/storage/timeline.rs) 的 `read_page`），所以一次分页调用至多这样还原三个请求：两个边界行（若为请求行）和它的第一个请求。

### 7.3 读取路径

```text
 read call (read_segments, read_page, a validation pass, read by id, trace)
   kept = none
   for each row, in sequence order, in today's segments:
     v16 request row  --refs--> content rows (#213 cache) --------------------------> request --+
     v17 request row  --list: last node -> parent -> ...                                       |
                        stop at the kept request's node at the same position, or at the first   |
                        at most 256 node loads per connection hold, through the cache          |
                      --kept.messages[..p] + loaded messages; tools, system by address --> request --+
                                                                   kept = request, in place <--+
     drafts of the row: the same walk against their record's request
```

### 7.4 成本，以及为什么不设上限

列表恰好是它的请求的消息。冷还原一个请求时，每条消息加载一个节点，此外什么都不加载，与之前的历史无关：不读其他请求行，不读后来被丢弃的消息，不读没有新增内容的 `model/call` 或重试行。没有需要限制的东西，所以 v17 不设深度上限，也不定期写完整副本。

在探针的数据库上测量（§12），五次取中位数；所读请求是该 Session 最后一个 `model/call`，冷读取；v16 一列是 `main` 上存储自己对该事件的读取：

| 配置 | 事件数 | 消息数与节点加载数 | v16 读取该事件 | v17 遍历列表（原型） |
| --- | --- | --- | --- | --- |
| 普通 | 1,001 | 199 | 0.55 ms | 0.89 ms |
| 普通 | 3,001 | 599 | 3.0 ms | 2.6 ms |
| 普通 | 10,001 | 1,999 | 9.7 ms | 14.4 ms |
| 工具 | 1,009 | 223 | 0.62 ms | 1.0 ms |
| 工具 | 3,007 | 667 | 3.4 ms | 3.0 ms |
| 工具 | 10,009 | 2,223 | 11.3 ms | 16.2 ms |
| 产品窗口 | 3,007 | 54 | 0.53 ms | 0.38 ms |
| 产品窗口 | 10,017 | 69 | 0.76 ms | 0.75 ms |

两者都是每条消息加载一条内容行，遍历耗时为 v16 读取同一请求的 0.7 到 1.65 倍：节点比 v16 的消息行大（带有父节点地址），原型也只用普通查询加载它。产品窗口中，请求受窗口限制，与历史长短无关。

合成列表把请求本身的大小与它之前的历史分开。一个临时程序在一次性数据库上把同一条链写成三种形式（release，Apple M4，SQLite 默认 2 MiB 页缓存，七次取中位数）：最后一个请求的 v16 引用、初稿的请求行间增量（§17）、v17 列表。每轮是一次新增两条 100 字节消息的 `context/prepare` 和一次不新增消息的 `model/call`；部分改写链中每次 prepare 还改写最后四条消息，对抗性链改写后一半。计时为冷还原最后一个请求：

| 链 | 最后一个请求的消息数 | v16 引用 | 初稿，一次递归查询，从最旧开始 | 初稿，向回遍历，每次持锁 256 行 | v17 列表，每次持锁 256 个节点 |
| --- | --- | --- | --- | --- | --- |
| 只追加 | 1,999 | 4.4 ms | 7.8 ms | 4.6 ms | 3.8 ms |
| 只追加 | 19,999 | 97 ms | 598 ms | 57 ms | 100 ms |
| 改写最后四条 | 1,999 | 4.5 ms | 9.3 ms | 5.6 ms | 5.6 ms |
| 改写最后四条 | 19,999 | 96 ms | 630 ms | 64 ms | 104 ms |
| 改写后一半 | 999 | 3.9 ms | 70 ms | 26 ms | 3.5 ms |

| 只追加，19,999 条消息，写入方每 2 ms 申请一次连接 | 最长连续持有连接 | 写入方最长等待 |
| --- | --- | --- |
| 初稿，一次递归查询 | 598 ms | 592 ms |
| v17 列表，每次持锁 256 个节点 | 1.7 ms | 1.3 ms |

- 初稿从最旧开始解码其链，并构建每个中间请求：对 `N` 条消息约 `N²/2` 次指针复制，19,999 条时为 199,980,001 次，占据其大部分耗时，使冷读取单个请求成为二次方。
- v17 在每条链中恰好每条消息加载一个节点。每次加载的成本从 2,000 条消息时的 1.9 µs 升到 20,000 条时的 5.0 µs，与 v16 每个引用的成本（2.2 到 4.9 µs）一样：两者都按内容地址查找，而内容地址在表的 B 树中是随机顺序，表越大页缓存未命中越多。
- 初稿的向回遍历按序号顺序经过事件行，20,000 条时每行仍约 2.8 µs。它在这里更快，但它读取其他请求的行，而检查点读取不得如此（§10），而且其成本随历史而不是随请求增长：每个请求改写后一半时，它要再次解析每条被改写的消息（999 条消息时 26 ms，列表为 3.5 ms）。

写入方记忆未命中（§6.2）是同一遍历，以同样的持锁区间在写事务之前进行：普通 10k Session 的 1,999 条消息为 14 ms，工具 Session 的 2,223 条为 16 ms，产品窗口中不到 1 ms，重启后每个分支一次。

仍有一项成本随两次压缩之间的调用次数呈二次方：每个已解码请求都携带其全部消息指针，这是事件类型的要求（`messages: Vec<Arc<Message>>`）。读取 10k 条普通事件的全历史要构建 2,000,000 个指针，约占原型 48.0 ms 中的 7.7 ms（§12）。v16 构建同样的向量；v17 去掉的是其背后的查找与解析。第 3 阶段（§15）去掉恢复期间整次读取的重复。

### 7.5 不使用请求正文的读取

分页或投影读取只返回事件所说的内容，不还原 `context/prepare` 与 `model/call` 存储的请求：这类记录中的请求保持其行所持有的空消息列表、缺席的 `tools` 与缺席的 `system`，它引用的内容行一律不加载、不校验 hash、不校验种类。这些读取从不查看这些请求：历史分页丢弃这两种记录，`session.summaries` 只读输入文本与最后一个事件的时间，上下文投影只投影输入与输出事实，协作只读工具调用、结果与轮次结局。协作取得对端 Session，通过其 query 只选择自己消费的事件种类，不选择模型请求行。端口只保留一个页读 `TimelineStore::read_page`，它会还原所返回行的请求；不读正文的变体已删除，因为不再有调用方绕过 Session 去提供存储事实。已装载线的历史分页改为经过该分支的 query，它会还原所返回行的请求（[ADR 020](../adr/020-timeline-read-convergence.md) D6）。使用请求的读取（`local`、`history`、`context`、`trace`、`validate_session`、导出）仍按 §7.1–§8 逐个还原并校验。

- 读取仍校验每条记录及其 before 轨迹的每个草稿是否带有其种类要求的引用，以及非请求记录是否没有引用；但它从不跟随这些引用。
- 因此损坏的节点不会让分页读取失败，因为该读取本来就不会加载它。恢复和每个使用请求的读取仍会在它上面失败，列表损坏的 Session 在恢复时仍被拒绝（§8）。
- 流式投影（§10）经分页读取历史，所以它投影的事件不携带存储的请求。估算所比较的那个请求是最后一个 `model/usage` 所度量的请求：它来自查询按该 usage 的 `request_id` 找到的 `model/call`，而不是来自被投影的事件。

## 8. 校验与损坏行

对每条请求记录，使用请求的读取检查以下各项，不满足时以存储错误失败（不使用请求的读取只检查第一项，即引用形状，§7.5）：

- `context/prepare` 或 `model/call` 记录及其每个请求草稿带 `References`（v16）或 `ListReferences`（v17）；其他记录为 `refs: null`；
- `ListReferences`：当且仅当 `length` 为 0 时 `list` 为 `null`，从 `list` 起的遍历恰好经过 `length` 个节点，最后经过的节点 `parent: null`，其余每个都有父节点；
- 每个节点都是种类 `node` 的内容行，地址与其正文的 SHA-256 相符，正文可解析为 `{parent, message}`；
- `tools` 与 `system` 地址解析到对应种类、hash 相符的内容行，与 v16 相同；
- 还原出的请求可解析为 `ModelRequest`。

在所保留请求处停下的按序遍历只校验它加载的节点；共享的节点在还原所保留请求时已校验。节点缺失或损坏时读取明确失败（“missing request content”“request content hash mismatch”“request list length mismatch”）；请求绝不会被还原为空或残缺。坏行保留原字节：读取从不写入。`validate_session` 对每一行做同样的检查，所以列表损坏的 Session 在恢复时被拒绝并保留，与现在内容行缺失时相同。一个损坏的节点会影响列表经过它的每个请求，正常情况下是从新增它的请求到下一次压缩为止的每个请求：也就是 v16 中引用同一条消息的那些请求。

## 9. 分支、分叉与删除

- **跨分支。** 子分支的第一个请求与最近一个有请求的祖先上截点及之前的最后一个请求共用节点；它只引用节点，从不引用祖先的事件行。父分支在截点之后继续写入时新增的节点不在子分支的任何列表中。
- **分叉**（[S5c §6.3](session-deletion-and-fork.md#63-分叉复制什么)）。截点及之前的 `main` 行逐字节复制。分叉照旧复制这些行引用的内容行，另外对每个 `list` 复制一直到第一个节点为止经过的每个节点：在分叉事务中对 `(session_id, hash)` 做一次递归查询，其 `UNION` 对多个列表共享的前缀只访问一次。截点之后的请求的节点不会被复制，除非某个更早的请求也共用它。复制的子分支目录 head 为 0，没有事件。复制仍是一个事务，其长度随 `main` 被复制的前缀增长，与 S5c 所述一致。分叉随后在 `at + 1` 写下的 `session/forked` 行不带请求、不引用内容，闭包不因它复制任何行。
- **删除与创建回滚**照旧删除该 Session 在每张表中的行；写入方丢弃该 Session 的记忆条目。

## 10. 压缩与检查点读取

完成的压缩改变列表开头，所以下一个请求与上一个请求没有公共前缀。它开始一个新列表，为每条消息（replacement、基线与保留的尾部）新增一个节点，数量受模型窗口限制。之后的请求延续它。产品窗口配置中，每次完成的压缩恰好开始一个新列表（§4.2）。

```text
 seq  event                      messages                         list
  30  input                      u18                              (resume of the snapshot below)
  37  model/call                 [u1 a1 ... u19]                  last node of u19, 37
  40  context/prepare            [u1 a1 ... u19 a19 u20]          2 new nodes, 39
  41  context/compaction-start
  42  context/compaction         completed: replacement S, retained from u18
  43  model/call                 [S b1 u18 a18 u19 a19 u20]       new list: 7 new nodes, at most the window
  50  context/prepare            [S b1 u18 ... u20 a20 u21]       2 new nodes, 9
```

锚定在 42 的快照记录 `resume` 30，即第一条保留的历史条目的事件。`resume` 不晚于该次压缩的 `through`（[timeline-storage §4](../../../architecture/rust-agent/timeline-storage.md#压缩检查点)、[history.rs](../../../../crates/dim-agent-capabilities/src/history.rs) 的 `projection_checkpoint`），所以 30 与 42 之间的请求行写入时还没有任何快照选定它，它们的列表一直回到 `u1`。

检查点读取照旧从 30 开始。其中第一个请求行由遍历该行自己的列表还原：只读内容行，每次持锁至多加载 256 个节点。不读取在 30 之前结束的任何行，也不读取 30 之前的任何请求行，这正是 [timeline-storage §4](../../../architecture/rust-agent/timeline-storage.md#有界读取与恢复扫描) 对检查点读取的约定。它加载的节点是该读取返回的请求的消息，v16 经这些行的引用加载的正是这些。之后的行（包括 43 处的新列表）从所保留的请求按序继续。

## 11. 格式 v17

**决定：版本 17，从恰好 v16 原地升级标记。不改表、列或索引，不读取或改写任何业务行。** 已在 [native-storage-format.md](../../../design/appserver/native-storage-format.md#格式版本) 记为提议；完整的格式决定随实现移入该文。

- **为什么需要新版本。** v16 守护进程读不了 v17 请求行：`References` 拒绝 `list` 与 `length` 且要求 `messages`，v16 读取方也不认识 `node` 内容。只有旧读取方能解释新数据时，格式才保持版本不变。
- **结构。** v16 的表保持原样；`agent_store_format` 改为 `CHECK (version = 17)`。`timeline_content.kind` 没有 SQL `CHECK`（存储在读取时检查），所以 `node` 种类无需改结构。
- **混存行。** v16 行保持写入时的样子，永久可读。升级后，分支的下一个请求行是 v17，其上一个请求是 v16 行，没有节点，所以这第一个 v17 行为每条消息写一个节点：每个分支一次完整列表，之后的请求共用它。两个版本的行可在同一分支、同一数据库中混存，分叉按原样复制它们。
- **`session/forked`。** #222 在 v16 下加入这一事件行，没有升版本号，所以在它之前构建的守护进程无法恢复 v16 库中被分叉的 Session。v17 原样保留这一行。这类守护进程都拒绝 v17 库，所以能打开 v17 库的守护进程都能解码它。

| 发现的存储 | 启动时动作，在现有准入事务内（`IMMEDIATE`，可写 PRAGMA 之前） |
| --- | --- |
| 空 | 创建 v17 结构，标记 17 |
| 精确的 v17 结构，标记 17 | 打开 |
| 精确的 v16 结构，标记 16 | 用 `CHECK (version = 17)` 重建 `agent_store_format` 并插入 17。仅此而已；失败时回滚到未动过的 v16 库 |
| 精确的 v15 或 v13 结构及其标记 | 现有步骤，然后执行本步骤，同一事务内 |
| 其他 | 照旧拒绝并保留 |

升级是单向的，与 S5a、S5b 的决定一致：v16 守护进程以现有的“unsupported SQLite schema … preserved”错误拒绝已升级的库。升级提交后，守护进程向 stderr 写一次 `Upgraded native store <path> from format v16 to v17; earlier dimcode versions cannot open it.`。在 `sqlite.rs` 中这是 `UPGRADES` 里的一项 `(16, &[])`，以及 `FORMAT = 17`。

不回填：转换 v16 行要读取并改写业务行，而升级不得如此；#213 已限制其读取成本。

| D1 | 消息是 `timeline_content` 中按内容寻址的列表节点；请求行引用其最后一个节点和长度 | 请求行之间的增量（本页初稿）；每条消息一个引用（v16） | 增量链经过更早的请求行，所以检查点读取会读 `resume` 之前的行，违反 timeline-storage §4，且其成本随历史而不是随请求增长（§7.4）。v16 随平方增长。列表保留 v16 的划分，读取只触及自己的行和所返回请求的内容 |
| D2 | 写入方与逻辑历史中紧邻的上一个请求共享前缀，先按指针再按 `==` 比较 | 前缀最长的更早请求；写入方手里还有的任意请求；逐字节比较 | 一条确定的规则；搜索会让字节依赖写入方的状态，且每次写入要扫描。逐字节比较要序列化每个 `context/prepare` 行的前缀，即 v16 的写入成本；按值相等是事件自己的还原合同 |
| D3 | `tools` 与 `system` 保持 v16 内容引用，与上一个请求相等时沿用 | 内联在行中；“同上一行” | 内容行本来就为它们寻址；沿用省去哈希；引用另一行会重新带回对更早行的读取 |
| D4 | 草稿以所在记录的请求为准编码为列表 | 草稿用 v16 引用 | 所在记录的请求在两端都在内存中，草稿也共用其节点 |
| D5 | 写入方记忆每分支一条固定大小的条目：位置、`Weak`、列表地址与长度、`tools` 与 `system` 地址；事务失败时丢弃、失效时清除 | 强引用记忆；不设记忆；保存全部节点地址的记忆 | 强引用会持有进程写过的每个 Session 的最后一个请求；没有记忆则每次写入都要回读上一个请求（§6.2）；保存节点地址会让条目随请求增长 |
| D6 | 不设深度上限，不定期写完整副本 | 每 N 个请求写一次完整列表 | 列表恰好是它的请求的消息，冷还原就是结果中每条消息加载一次（§7.4）；定期副本只会重复内容 |
| D7 | 节点是现有表中按内容寻址的行 | 新表中以整数寻址的节点 | 不改 SQL；v16 的寻址、hash 校验与分叉闭包原样适用。按创建顺序分配的整数地址遍历时有顺序局部性（初稿的行遍历在 20,000 条时每步 2.8 µs，节点加载为 5.0 µs），但需要一张表、一个 ID 分配器和自己的完整性检查，而收益只在任何实测配置之外才出现 |
| D8 | 遍历列表每加载至多 256 个节点就释放连接 | 每次遍历一次查询或一次持锁 | timeline-storage §4 的有界分段；20,000 条消息时一次递归查询持有连接 598 ms（§7.4） |
| D9 | v16 行保持写入时的样子 | 升级时或惰性转换 | 升级不读取或改写任何业务行（§11） |
| D10 | 写入方在写事务之前经读取路径读取所需的上一个请求 | 在事务内还原 | 这样事务只为新节点和该行持有连接；在事务内还原会在每次重启后为整个列表持有连接（§6.1） |

## 17. 否决的方案

- **请求行之间的增量**（本页初稿：行保存其 base 行的位置、保留长度，其余消息内联）。还原一个请求要读回上一次压缩以来每个更早的请求行，所以从 `resume` 起的检查点读取会读 `resume` 之前的请求行（timeline-storage §4），一次递归查询还在整条链期间持有连接。从最旧开始解码时单个请求为二次方；向回解码时与链长成线性，但链随历史增长：没有新增内容的行和后来被改写的消息都要计入（§7.4）。
- **推导请求而不保存**：`model/call` 是交给模型的最终请求（ADR 005 D1），ContextPolicy 读取精确的最近请求；推导是同一事实的第二个生产方。
- **事件中的惰性请求句柄**：改变事件类型和所有使用方，并把存储错误带进期待已校验数据的读取方（AGENTS.md 数据约定）。
- **按种类过滤的读取**（为不关心请求事件的能力跳过它们）：改变读取 API 与各能力的重建，且二次方的存储依然存在。
- **能力快照**用于重建：在每个插件里为优化增加业务状态（timeline-storage §4）。
- **存储范围的已解码事件缓存**：驻留会随每个已装载或最近读取的 Session 增长，违反空闲分支验收。
- **把 `ModelRequest.messages` 改为持久化数据结构**：为了指针复制这一项（§7.4）改变事件类型及其冻结合同。

## 18. 验收

实现 PR 须全部通过，且只使用一次性数据库。行为检查在存储流程中运行；耗时与大小阈值用 `restore_cost` 测量，并在实现 PR 中报告，不在测试中断言。所用流程是现有的（`storage_flow.rs`，进程中断与断电用 `timeline_acceptance`），不为每一条单独写测试。

沿用自 [timeline-storage §7](../../../architecture/rust-agent/timeline-storage.md#7-验收)：

1. **存储还原。** 读回的事件与写入的逐字段一致，覆盖跨写入轮追加的输出行、原子批次与 before 轨迹，另外覆盖：压缩后的新列表；保留上一个请求一部分与全部的请求；`system` 与 `tools` 缺省、沿用与变化；请求草稿不变、追加一条消息、改动早期消息、改动 system prompt；从父分支和祖父分支共享的列表，且父分支在截点后继续写入；混存行（升级后继续的 v16 Session，其第一个 v17 行写一次完整列表）；以及在混存 `main` 的截点处分叉，分叉的读取等于源的前缀，其内容行恰好是其各行引用的闭包。
2. **长会话驻留。** 2,000 步、800 KB 上下文：空闲分支的存活字节不随步数增长，准备期间的峰值不随压缩前的历史增长。Session 卸载后，写入方记忆不再持有它的任何存活请求。
3. **分页与恢复。** 长历史页读不先解码全量；从历史中间开始的页只遍历其第一个请求的列表；合并行、批次与跨页 ToolCall 仍然正确。恢复缓存有界（每次读取一个保留的请求及其节点地址，以及 #213 的缓存），长冷读取不占用连接以致阻塞写入。
   - **3a. `resume` 之前历史很长、且有并发写入方时的检查点读取。** 一个 Session 在某次压缩之前有 2,000 个请求行，其快照的 `resume` 位于压缩之前几轮。快照保存后，在一次性数据库中把在 `resume` 之前结束的每个事件行的正文改写为无效 JSON；经检查点、只取上下文的 `HistoryRenderer::context` 仍返回与改写前相同的 `ContextHistory`，所以没有读取这样的行。存储从 `resume` 起的读取恰好加载第一个请求的节点数加上之后各请求的新节点。该读取冷运行期间，向另一个 Session 追加的写入方每次等待不超过一次 256 个节点加载的持锁。
   - **3b. 单个请求。** 2,000 与 20,000 条消息的列表，只追加与每轮改写最后四条消息两种：冷读取最后一个请求加载的节点数恰好等于其消息数，每次持锁至多加载 256 个节点，耗时不超过同一台机器上 v16 读取相同消息的请求的两倍（§7.4 实测为 0.7 到 1.65 倍）。重启后在这样的分支上写入的第一个请求以同样的持锁区间读取其上一个请求，其写事务不加载任何节点。
4. **进程中断与断电。** 在提交前、提交后发布前、发布后终止：恢复的事件能读回，序号连续，没有行引用未提交的节点。重启后（记忆为空）写出的字节与未中断的运行相同。
5. **存储故障。** 注入读取失败与提交失败时行为照旧；提交失败后，重试与之后的批次只相对已提交的行与节点编码，字节与未发生故障的运行相同。
6. **损坏。** 节点缺失、节点 hash 不符、节点种类不符或正文无法解析、列表比 `length` 长或短、`list: null` 而 `length` 非零、`ListReferences` 格式错误，以及 `tools` 或 `system` 地址种类不符：每种都让 `read`、`read_page` 与 `branches` 以存储错误失败；该行保留原字节，没有请求被读回为空。同样的损坏位于 2,000 条消息的列表中间时，列表经过它的每个读取都失败，而之后某次压缩开始的列表中的请求仍可读取。#213 的内容损坏用例仍然失败。

新增：

7. **两次压缩之间的大量模型调用。** 普通与工具 Session 不压缩地增长到约 1k、3k、10k 条事件（`restore_cost`）。报告每个规模下的恢复加首次 idle、每次读取耗时与每条事件的字节数，并与 #213 的数据对照。10k 时每条事件的字节数与 1k 相差不超过 10%，普通轮 10k 条事件时，每次读取耗时不超过 #213 的 40%，恢复加首次 idle 不超过其一半（此处所用机器上为 1,779 ms），在同一台机器上测量。产品窗口配置中，每次读取耗时不超过 v16 的 1.2 倍，每条事件的字节数低于 v16。
8. **确定性。** 同一段历史（含子分支、一次压缩与请求草稿）分别在启用写入方记忆、禁用记忆（`testing` 钩子）、中途重启的情况下写入，`timeline_events` 与 `timeline_content` 各行逐字节相同。
9. **冻结合同。** `crates/dim-agent-types/tests/fixtures/` 与 `*_contract.rs` 测试不被改动，且通过。
10. **升级。** 空库建为 v17。一次性 v16 库原地升级为精确的 v17 结构，所有行逐字节不变，并只报告一次；v15 与 v13 库在一个事务内到达 v17；标记不符、升级到一半、更旧与未知的结构被拒绝并保留；v16 守护进程拒绝 v17 库时使用现有错误。
